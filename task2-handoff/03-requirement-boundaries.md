# 第二道能力验证题｜需求边界与优先级

> 分类规则：P0 只含原始题目明确要求；P1 是没有它就很难真实、完整地实现某个 P0 的能力；P2 是可选加分项。  
> P1/P2 均不是“甲方原话”。任何范围变化必须记录来源和批准状态。

## P0：原始题目明确要求

| ID | 要求 |
| --- | --- |
| P0-01 | 复刻 Creen.ai 网站 |
| P0-02 | 完整注册 |
| P0-03 | 完整一方登录 |
| P0-04 | Google 三方登录 |
| P0-05 | 完整跨模态计费系统 |
| P0-06 | 支持真实调用，非 Mock |
| P0-07 | 支持 Stripe 支付 |
| P0-08 | 各主要页面完整复刻 |
| P0-09 | 学习并实现其 SEO 逻辑 |
| P0-10 | 保留过程记录 |

## P1：为实现 P0 很可能必须存在的能力

P1 的具体实现方式仍是 `TBD after research`。

| ID | 推导能力 | 来源 P0 | 为什么需要 | 尚未确定 |
| --- | --- | --- | --- | --- |
| P1-01 | 用户身份、账号与会话的持久化 | P0-02/03/04 | 注册和两类登录需要识别同一用户并维持受保护会话 | 用户字段、会话形态、账号合并策略 |
| P1-02 | 第一方凭证的安全存储与校验 | P0-02/03 | “完整”的第一方注册登录不能保存明文凭证或只做前端判断 | 登录标识、认证库、密码/无密码方案 |
| P1-03 | Google OAuth/OIDC 配置、回调和错误处理 | P0-04 | Google 登录必须与真实 Google 身份链路交互 | SDK、回调路由、授权范围、账号冲突策略 |
| P1-04 | 受保护页面/API 与退出、过期处理 | P0-02/03/04 | 登录必须对实际产品访问权限产生作用 | 哪些页面受保护、Session 时长 |
| P1-05 | AI Provider 服务端集成和密钥管理 | P0-05/06 | 真实模型调用不能在浏览器暴露密钥，也不能返回假结果 | Provider、模型、密钥托管方式 |
| P1-06 | 跨模态任务的统一用量事件 | P0-05/06 | 计费必须知道谁在何时调用了哪种模态、计量多少、成功与否 | 模态、计量单位、任务状态模型 |
| P1-07 | 价格/额度规则的版本化与可追溯账本 | P0-05 | “完整计费”需要解释每次扣费依据并避免余额仅靠前端显示 | 价格、余额/后付费模式、精度与币种 |
| P1-08 | 计费与 AI 任务的幂等、失败补偿和并发一致性 | P0-05/06 | 重试或并发不能重复扣费，失败调用不能形成错误账目 | 预扣/后扣方案、事务边界 |
| P1-09 | Stripe 官方集成与服务端支付状态 | P0-07 | 静态付款按钮不构成 Stripe 支付；服务端必须知道可验证的支付结果 | Checkout/Payment Element、一次性/订阅、测试/生产环境 |
| P1-10 | 支付状态的可信同步机制 | P0-07 | 用户跳转回页面不足以证明支付最终成功 | Webhook 是候选方案，但是否采用及事件清单待方案确认 |
| P1-11 | Creen.ai 页面、导航与响应式基线清单 | P0-01/08 | 未先定义“主要页面”就无法验收“完整复刻” | 页面范围、登录后可见页面、复刻精度 |
| P1-12 | SEO 可观察证据与实现映射 | P0-09 | SEO 不能只写关键词，需要把研究发现映射到可验证实现 | 渲染策略、metadata、结构化数据、URL/内链策略 |
| P1-13 | 第三方失败、限流、超时和用户安全错误 | P0-04/06/07 | Google、AI、Stripe 都会失败；完整流程必须可恢复且不泄密 | 重试策略、超时、降级边界 |
| P1-14 | 环境配置与秘密隔离 | P0-04/06/07 | 真实集成必然涉及凭证，不能提交仓库或下发客户端 | 部署平台和秘密管理服务 |
| P1-15 | 可复现的测试、运行说明和阶段记录 | P0-10，以及全部 P0 | 过程记录需要证明调研、决策、实现和验证确实发生 | 文档载体和 CI 平台 |

以下项目只有在调研证明 Creen.ai 主要范围包含、为 P0 验收确有必要，或题目提供方明确同意后，才可升级为 P1/P0。

## 变更规则

1. 新需求进入范围前必须标注来源：`Original`、`Derived`、`Research finding` 或 `Stakeholder confirmed`。
2. P1 必须关联至少一个 P0，并写清“不实现会导致什么 P0 无法成立”。
3. P2 默认不排期；不得因为框架模板自带或 AI 容易生成就偷偷加入。
4. 关键 Unknown 在架构冻结前必须转成已确认决定、明确排除或保留的 TBD，并记录负责人和确认时间。
